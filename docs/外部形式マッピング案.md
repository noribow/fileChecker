# 外部形式マッピング案（検討中）

`docs/open-decisions.md` の **3.1 外部形式（CSV/XML等）のフィールドマッピング仕様** に対する検討資料。
「対象とする外部ツールの洗い出しが先」という前提調査として、MAMEが公開する2種類のXML/DTD形式を
事例に検討した。まだ`docs/requirements.md`には確定事項として反映していない、レビュー用のドラフト。

対応するお手本セット側のスキーマ: `docs/requirements.md` §10.12 の `reference_set` / `reference_file`
（`path` / `size` / `crc32` INTEGER / `md5` BLOB / `sha1` BLOB / `sha256` BLOB、いずれも提供された
アルゴリズムのみ埋める設計）。

## 事例1: MAME softwarelist.dtd

出典: https://github.com/mamedev/mame/blob/master/hash/softwarelist.dtd
（1ソフトウェアタイトル＝1アーカイブという構造。カートリッジ/ディスク単位のソフトウェア一覧）

### 階層構造
```
softwarelist (name, description?)
 └─ software+ (name, cloneof?, supported)
     ├─ description / year / publisher / notes? / info* / sharedfeat*
     └─ part+ (name, interface)
         ├─ feature*
         ├─ dataarea* (name, size, width, endianness)
         │    └─ rom* (name?, size?, crc?, sha1?, offset?, value?, status, loadflag?)
         ├─ diskarea* (name)
         │    └─ disk* (name, sha1?, status, writeable)
         └─ dipswitch* (name, tag, mask) └─ dipvalue*
```

### フィールドマッピング

| DTD要素/属性 | File Checker側 | 備考 |
|---|---|---|
| `rom@name` | `reference_file.path`（一部） | `{software@name}.zip/{rom@name}`が基本形 |
| `rom@size` | `reference_file.size` | そのまま |
| `rom@crc` | `reference_file.crc32` | 16進文字列→INTEGER変換 |
| `rom@sha1` | `reference_file.sha1` | 16進文字列→BLOB変換 |
| `disk@name`/`@sha1` | 同上のdiskarea版 | 同様 |
| — | `md5`/`sha256` | DTDに相当項目が無く常にNULL |

### マッピング対象外（不要と判断した項目）

`softwarelist@name/description`、`software@description/year/publisher/notes/info*/sharedfeat*`
（書誌情報）、`software@cloneof`（ROM系譜）、`software@supported`（MAMEのエミュレーション対応状況）、
`part@interface`/`feature*`（ハードウェアスロット種別）、`dataarea@size/width/endianness`
（メモリバス構成）、`dipswitch*`/`dipvalue*`（DIPスイッチ設定）、`disk@writeable`（可変ディスクは
ハッシュが不変でなく整合性チェック対象になり得ない）。

### 単純な列マッピングでは済まない論点
- **`rom@loadflag`**（reload/continue/fill/ignore等）: 「別チャンクの再利用」「実ファイルを伴わない
  定数埋め」を表し、素直に取り込むと存在しないファイル・重複ファイルが紛れ込む。除外フィルタが必要。
- **`rom@status`/`disk@status`**（baddump/nodump/good）: `nodump`はcrc/sha1自体が無く除外必須。
  `baddump`は「不正確と分かっているダンプ」で、そのまま基準値にするかは要判断。

## 事例2: MAME mame.dtd（機種本体のROMセット定義）

ユーザー提供のDTD全文を検討（1機種＝1アーカイブ、`<mame><machine>...`構造）。

### フィールドマッピング（事例1と同型）

| DTD要素/属性 | File Checker側 | 備考 |
|---|---|---|
| `rom@name` | `reference_file.path`（一部） | `{machine@name}.zip/{rom@name}`が基本形（`merge`属性の例外あり、後述） |
| `rom@size`/`@crc`/`@sha1` | `size`/`crc32`/`sha1` | 事例1と同様の変換 |
| `disk@name`/`@sha1` | 同上のdisk版 | 同様 |
| — | `md5`/`sha256` | 事例1と同じく常にNULL |

### マッピング対象外
書誌情報（`description`/`year`/`manufacturer`）、系譜・分類フラグ（`cloneof`/`sampleof`/`isbios`/
`ismechanical`）、ハード仕様全般（`chip*`/`display*`/`sound`/`input`・`control*`/`port`・`analog*`/
`adjuster*`）、設定項目（`dipswitch`系/`configuration`系/`ramoption`）、エミュレーション品質評価
（`driver`）、スロット・周辺機器定義（`device`系/`slot`系/`device_ref`）、機種直下の`softwarelist`要素
（ルート要素と同名だが別物 — 対応ソフトリストへの関連付けに過ぎない）、`sample@name`（ハッシュ・
サイズ情報が一切無く基準値化不可）。

### 事例1には無かった、より厄介な論点
- **`rom@merge`/`disk@merge` + `machine@romof`**（親子ROMセットの共有）: クローン機は親と同一のROMを
  自分のzipに含めず`merge`属性で親のROM名を指すだけで済ませる運用が一般的。`romof`の連鎖を辿って
  実体の所在（どのzipのどの名前か）を解決しないと、存在するファイルを「欠落」と誤判定する。
- **`rom@bios`**（選択式BIOS）・**`rom@optional`**（任意ROM）: 列挙されている＝必須ではない例。
  複数候補のうち1つだけ必須、あるいはそもそも任意、という欠落判定の緩和ルールが要る。
- **`machine@isdevice`**: サブ基板的な内部デバイス定義。単体の「ソフトウェア／ファイル群」として
  扱うかは用途次第。

## 2事例から得られた共通の知見

- **列対応部分は単純かつ共通**: `rom`/`disk`の`name/size/crc/sha1` → `reference_file`のflat列という
  対応はほぼ同一パターンで、両形式ともmd5/sha256は存在せず常にNULLになる。
- **本質的な難しさは列対応ではなく「包含判定」**: 「このエントリは本当にこのアーカイブ内に実ファイル
  として存在するはずか」という除外・解決ロジック（事例1: loadflag/status、事例2: merge/romof/bios/
  optional/isdevice）が両形式に共通して存在し、単純なフィールドマッピング表では表現しきれない。
  形式ごとに個別の判定ロジックをアダプタ実装に持たせる必要がある。
- **パス表現**: いずれも「1エントリ＝1アーカイブ、中身は複数ROM/ディスクファイル」という構造で、
  File Checkerのアーカイブ内エントリ表現（`parent > child`、§10.14）と相性がよい。

## 実装に向けた残課題（未決事項）

1. **loadflag起因の除外ロジック**（事例1）: reload/continue/fill/ignore等、実ファイルを伴わない
   `rom`要素をインポート時にどう判定・除外するか。
2. **status=nodump/baddump の扱い**（事例1・2共通）: `nodump`は除外必須。`baddump`をデフォルト除外
   にするか、警告付きで取り込みユーザーに選ばせるか。
3. **rom@merge / machine@romof のROMセット共有解決**（事例2）: 親子アーカイブをまたぐパス解決に
   完全対応するか、v1では非マージ（フルセット/split以外）構成のみサポートとして割り切るか。
4. **rom@bios / rom@optional の表現**（事例2）: 「複数候補中1つだけ必須」「そもそも任意」を
   `reference_file`側でどう表現するか。既存スキーマ（§10.12）には該当カラムが無く、対応する場合は
   `optional`フラグや代替グループ列の追加など**スキーマ変更を伴う可能性がある**。
5. **machine@isdevice=yes の扱い**（事例2）: インポート対象から除外するか、別アーカイブとして扱うか。
6. **disk@writeable/@writable の除外**（事例1・2共通、属性名の綴りが形式間で異なる点にも注意）:
   可変ディスク（セーブデータ等）は整合性チェックの基準値になり得ないため除外。
7. **md5/sha256が存在しない形式での整合性チェック運用**: §10.1で自前形式生成時はSHA-256必須として
   いるが、外部形式インポート時はCRC32/SHA1のみで照合する運用になる。GUI/CLI上でこの違い（どの
   アルゴリズムで照合されたか）をどう明示するかも合わせて検討が必要（§10.14結果一覧への表示要否）。
8. **要素名の意味衝突**: 事例2の`softwarelist`要素は事例1のルート要素と同名だが意味が異なる。
   アダプタ実装は形式ごとに独立したスコープで解釈する必要がある（要素名だけでなく形式全体で
   マッピング定義を持つ設計であることの確認）。
9. **対象外部ツールの洗い出し継続**: 今回の2例はいずれもMAME系（ROM/ディスクイメージのアーカイブ
   検証という点でFile Checkerと親和性が高い題材）。3.1を完全に閉じるには、他にどの外部ツール
   （例: 一般的なチェックサムツールのCSV出力、他のアーカイブ管理ツールのXML等）を優先的に
   サポートするかの洗い出しが引き続き必要。
