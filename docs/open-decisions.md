# 決定すべき要件 タスクリスト

`docs/requirements.md` の「9. 未決事項」を、依存関係を考慮して着手すべき順に整理したもの。

## 1. コア処理の基本方針（最優先・他の決定のブロッカー）

- [x] **1.1 ハッシュアルゴリズムの選定** — 決定済み（`docs/requirements.md` 10.1参照）
  - 外部お手本セット読み込み用にCRC32・MD5・SHA-1・SHA-256の4種を実装。自前形式の生成・重複チェック最終確定にはSHA-256を標準採用。
- [x] **1.2 重複判定アルゴリズムの方式** — 決定済み（`docs/requirements.md` 10.2参照）
  - サイズ一致 → CRC32(全体) → SHA-256(全体)確定の2段階方式。部分ハッシュ（ファイル先頭等）は不採用。

## 2. データ永続化設計

- [x] **2.1 SQLiteスキーマ設計** — 決定済み（`docs/requirements.md` 10.12参照）
  - `scan_run`（情報取得）と`check_run`（比較実行）を分離し、`check_run_source`で複数の`scan_run`（新規・
    過去の保存済み分の混在可）を束ねる構成とする。ハッシュ値は`scanned_file`/`reference_file`に列持ち
    （正規化しない）、`crc32`はINTEGER・`md5`/`sha1`/`sha256`はBLOB。アーカイブ内ネストは`scanned_file`への
    自己参照で表現。お手本セットは`supersedes_reference_set_id`で版管理。整合性チェック結果ステータスは
    10.11の5種（ok/corrupted/missing/extra/error）。`docs/DBスキーマ案.md`は確定版のベースとなったレビュー
    用ドラフトとして残す。
  - 追記（`docs/requirements.md` 10.15）: アーカイブ自体の展開に失敗した場合、その内部に期待される
    お手本セットのエントリは`missing`ではなく`error`として記録する（スキーマ変更なしで表現可能）。
- [x] **2.2 リムーバブルメディアの識別方法** — 基本方針は決定済み（`docs/requirements.md` 10.4参照）
  - OSごとに切り替え可能な識別ロジック（プラットフォーム抽象化）とし、スキーマ上は `identifier_type` + `identifier_value` + `platform` の抽象形式で保持する。OS別の具体的な取得優先順は各OS実装時に定める。
- [ ] **2.3 リムーバブルメディア識別のフォールバック方針**（識別子を安定的に取得できない／信頼できないメディアへの対応）
  - 2.2から切り出した残課題。緊急度は低く、将来検討でよい（`docs/requirements.md` 10.4参照）

## 3. お手本セット定義ファイルの外部連携

- [x] **3.1 外部形式（CSV/XML等）のフィールドマッピング仕様** — 現状の仕様で決定・検討終了
  （`docs/requirements.md` 10.18参照）
  - 前提調査として、MAMEの2形式（`softwarelist.dtd`／`mame.dtd`）を事例に検討した
    （詳細: `docs/外部形式マッピング案.md`）。`rom`/`disk`要素の`name/size/crc/sha1` →
    `reference_file`の`path/size/crc32/sha1`という基本マッピングは共通で、両形式ともmd5/sha256は
    存在せず常にNULL。
  - **確定した処理方針**（MAME向け）: loadflag起因エントリ（fill/reload/continue/ignore）は除外、
    status=nodumpは除外必須・baddumpはデフォルト除外＋オプションで含める、rom@merge/machine@romofは
    取り込み時にmerged/split形式をユーザーが明示選択、bios/optionalは除外（スキーマ変更なし）、
    machine@isdevice=yesは常に除外、disk@writeable/writableは常に除外、要素名衝突対策として形式ID単位で
    独立したマッピングテーブルを持つ。
  - **見送り**: 照合アルゴリズム（md5/sha256非対応形式）のUI明示は今回は行わない。
  - **次バージョン以降の課題**: MAME系以外の外部ツールの洗い出し・対応拡張は次バージョンで検討する
    ことで3.1を区切り、検討終了とした。

## 5. 横断的な方針

- [x] **5.1 エラーハンドリング方針** — 決定済み（`docs/requirements.md` 10.17参照）
  - ファイル単位のエラーはアクセス不可/権限エラー・アーカイブ展開エラー・パスワード復号失敗をリトライ
    なしで即座にスキップ・記録、I/Oエラー（一過性障害）のみ固定3回・指数バックオフでリトライしてから
    スキップ・記録する。いずれもスキャン・比較全体は中断しない。記録はSQLite DB（`error_message`列、
    簡潔な一行サマリ）に加え、実行単位のテキストログファイル（詳細な診断情報）も出力する。DB接続失敗・
    対象不在等の実行単位エラーはリトライ対象外で即座に全体中断（CLI終了コード3）。CLI終了コード2
    （検証不能あり）は原因別に細分化しない。

## 6. 圧縮ファイル対応

- [x] **6.0 対応する圧縮ファイル形式** — 決定済み（`docs/requirements.md` 10.5参照）
  - zip・7zを対象とし、それぞれzstd圧縮方式にも対応する。読み取り（展開・ハッシュ照合）が必須機能、書き出し（再構成）は別機能として扱う。
  - 将来の対応形式拡張を見込み、DBスキーマ（`scanned_file.archive_format`）はCHECK制約等で形式を固定しない自由文字列とし、形式の妥当性判定はアプリケーション層で行う。
- [x] **6.1 圧縮ファイル展開時の安全対策** — 決定済み（`docs/requirements.md` 10.6参照）
  - 再帰展開は最大3階層。エントリ展開時はアーカイブ記載の宣言サイズを超えないことを検査。展開後サイズ上限は現時点で2TB。いずれも将来変更可能な設定値として保持し、ハードコードしない。
- [x] **6.2 暗号化・パスワード保護された圧縮ファイルの扱い** — 決定済み（`docs/requirements.md` 10.7参照）
  - アプリ設定でユーザーが「エラーとする」/「登録済みパスワードで復号を試行する」を選択可能にする。パスワードは形式ごとの個別設定・一括設定の両方に対応（実装方法は6.4で検討）。
- [x] **6.3 お手本セットに合わせた再構成（圧縮ファイル書き出し）機能の詳細仕様** — 決定済み
  （`docs/requirements.md` 10.19・10.20参照）
  - TorrentZip/Torrent7zのフォーマット仕様について、ユーザー提示のPDF2件（romvault.com）を調査し
    `docs/TorrentZip_Torrent7z仕様調査.md` にまとめた。TorrentZip（zip向け）は実装レベルで完結した
    決定的仕様（固定タイムスタンプ・小文字ソート順・zlib 1.1.3相当レベル9・EOCDコメントによる
    検証マーカー等）を確認済み。一方Torrent7z（7z向け）側は、提示資料が汎用7zコンテナ構造の解説
    （かつ末尾が未完成）にとどまり、決定的出力に必要な固定パラメータが含まれていなかった。
  - 追加調査として実装リファレンス [RomVault/RVWorld](https://github.com/RomVault/RVWorld)
    （Apache-2.0）の`Compress/StructuredZip`等を確認し、7z側の固定パラメータ（LZMA固定・
    辞書サイズ決定関数・numFastBytes=64・タイムスタンプ非記録・`Trrnt7ZipStringCompare`による
    拡張子→名前→パスの3段階ソート順）はほぼ判明した。調査の結果、RomVaultの現行実装は元祖
    "Torrent7z"（`torrent7z_0.9beta`検証形式）の書き出しを既にやめ、独自後継形式
    「RomVault7Zip（RV7Z）」（検証マーカーが異なる）に移行済みであることが判明していた。
  - **生成フォーマット決定（2026-09-04）**: 7z側の生成フォーマットは**RV7Z**（Solid-LZMA /
    `SevenZipSLZMA`）を採用する（`docs/requirements.md` 10.19参照）。元祖`torrent7z_0.9beta`
    レガシー形式には準拠しない。
  - **トリガー条件・対象範囲・実行フロー決定（2026-09-04）**: 整合性チェック結果一覧から起動し、
    再構成先フォルダ＋既存`scan_run`群を束ねた`check_run`で充当計画を算出、ユーザー承認後に実行する
    （`docs/requirements.md` 10.20参照）。複数`scan_run`が同一ファイルにヒットする場合の優先順位
    （再構成先ローカル→他の内部ドライブ→リムーバブルメディアは最新スキャン優先）を新規に一般ルール
    として確定（通常の整合性チェックでは、この優先順位はあくまで既スキャン済みデータの中から選ぶ
    ためのものであり、リムーバブルメディアの暗黙の再接続要求は行わない）。`missing`が残っていても
    実行はブロックせず部分的に再構成する。リムーバブルメディアはメディア単位でまとめて読み取り、
    エラー分はそのメディア内で再試行してから次のメディアへの差し替えを促す。DBスキーマに
    `reconstruction_run`/`reconstruction_item`の2テーブルを追加（`scan_run`/`check_run`とは別の
    「計画済み充当元からの書き出し実行」という第三の実行単位）。GUI・CLI（`reconstruct plan`/
    `reconstruct run`/`reconstruct status`）双方に対応。
  - **残る未決事項**: 非Solid版・ZSTD版7z（`NLZMA`/`SZSTD`/`NZSTD`）への対応要否、再構成先に同名
    別内容ファイルが既存する場合の上書き/退避方針は本節の対象外として残る（10.20参照）。
- [x] **6.4 登録パスワードの保存方式・登録UI** — 基本方針は決定済み（`docs/requirements.md` 10.9参照）
  - SQLite DBには含めず、アプリの設定フォルダ内の専用設定ファイルに保存する。OSキーチェーン連携等の高度な管理は行わない。パスワードの確認・追加・削除を行う専用のGUI管理画面を設ける。
  - 設定ファイル自体の具体的な保護方式（プレーンテキスト／難読化／暗号化）は未決事項として残る（6.5として切り出し）
- [x] **6.5 登録パスワード設定ファイルの保護方式** — 決定済み（`docs/requirements.md` 10.10参照）
  - ソース公開前提のため、コード埋め込み鍵やOSアカウント紐づけのみでは実質的な保護にならない。ユーザーが設定するマスターパスワードからArgon2id（既定候補）でKDF導出した鍵で暗号化する。マスターパスワードは無保存、検証用にソルト付きハッシュのみ保持。忘れた場合の復元手段はなく、設定ファイルをリセットして再登録する運用とする。GUIにマスターパスワードの設定・入力・変更・リセット画面を追加。
