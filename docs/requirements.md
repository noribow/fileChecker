# File Checker 要件定義書（修正版）

## 1. 概要・目的

File Checker は、巨大なファイル群を対象に、以下の2つの課題を解決するためのツールである。

- 整合性チェック: ファイルの破損・欠落・改変を検出し、お手本セットとして定義された正規データと照合する。
- 重複チェック: 複数フォルダやリムーバブルメディアを横断して、内容が同一のファイルを検出する。

本ツールは、写真・動画・バックアップデータなどの大容量データを扱うユーザーが、ディスク全体の状態を効率的に把握し、修復・整理・保守を行えることを目的とする。

## 2. 対象プラットフォーム

- Windows（Tier-1、最優先の検証対象）
- macOS（Tier-2）
- Linux（Tier-2）

## 3. 機能要件

### 3.1 整合性チェック

#### 3.1.1 基本動作

- ツールは対象フォルダを走査し、ファイル名・ファイルサイズ・ハッシュ値を収集する。
- 収集した情報を、お手本セット定義ファイルと比較して、欠落・破損・改変・不一致の有無を判定する。
- 比較結果は、個別ファイル単位での状態を識別して出力する。

#### 3.1.2 判定状態

整合性チェックで扱う状態は以下のとおりとする。

- OK: お手本セットと一致している
- MISSING: お手本セットには存在するが、対象フォルダに見当たらない
- MODIFIED: ファイルは存在するが、サイズまたはハッシュが一致しない
- EXTRA: 対象フォルダに存在するが、お手本セットに定義されていない
- UNREADABLE: ファイルの読み取りに失敗した

#### 3.1.3 ファイル比較の正規化ルール

比較対象の定義を明確にするため、以下のルールを適用する。

- パスはシステムの標準的な正規化方式で比較する
- シンボリックリンクは既定で追跡対象外とし、リンク自体は別扱いとする
- ハードリンクは、実体ファイルとして個別に扱うか、重複判定の対象に含めるかをルール化する
- Windows/macOS/Linux での大文字小文字の扱いは、それぞれの OS 標準に従う
- Unicode 正規化済みのパスを比較対象とし、同名異表記のファイルは別件として扱う
- アクセス権限のないファイルは、比較不能として記録する

これにより、OS 差異やリンクの扱いによる誤判定を防止する。

### 3.2 重複チェック

#### 3.2.1 基本動作

- ユーザーが指定した複数のフォルダ、または複数のリムーバブルメディアを対象に、重複ファイルを検出する。
- 1 つのスキャン対象内で重複するファイル群、および複数対象間で重複するファイル群を両方検出する。
- 検出対象は、ファイルの内容が一致するものとし、同一パスの重複は重複とみなさない。

#### 3.2.2 重複判定アルゴリズム

重複判定は次の段階で行う。

1. まずファイルサイズで候補を集約する
2. サイズが一致したファイル群に対して、ハッシュ値を計算して比較する
3. ハッシュ値が一致したファイル群を重複グループとして確定する

この方式を採用する理由は、フル比較より高速かつメモリ効率に優れるためである。

- 低コストな候補絞り: サイズ一致で前処理を行う
- 正確な判定: 同一ハッシュ値による最終判定を行う
- 例外: 同一サイズで別内容のファイルが存在する場合でも、ハッシュ比較により正しく区別する

#### 3.2.3 リムーバブルメディアの扱い

- リムーバブルドライブ、USB メモリ、「PR コメント向けの返信文」外付け HDD を対象に含める
- メディア接続時にスキャンを実行し、結果を保存する
- 再接続時には、過去のスキャン結果を再利用できるようにする
- 既知のメディア識別子が一致する場合は、再スキャンを省略し、メディアごとの履歴比較を可能にする

#### 3.2.4 重複結果の出力

重複判定の結果は、以下の粒度で出力する。

- 重複候補ファイル一覧
- 重複グループ一覧
- 1 つのファイルがどのグループに属するか
- 重複ファイルの元/コピー候補の識別

### 3.3 お手本セット定義ファイル

#### 3.3.1 形式

- 自前形式は JSON とする
- 外部形式の取り込みは CSV / XML を対象とし、アダプタ機構を用意する

#### 3.3.2 自前形式の定義

JSON 形式では、次の要素を持つファイルとして定義する。

- set_name: お手本セット名
- generated_at: 生成日時
- files: ファイル情報の配列
  - path: ファイルの相対パス
  - size: ファイルサイズ（bytes）
  - sha256: SHA-256 ハッシュ値

#### 3.3.3 外部形式の読み込み

- CSV / XML 形式の外部定義ファイルを読み込むインターフェースを提供する
- フィールドマッピングのルールを明示する
- サポート対象外のフォーマットは、読み込み失敗として記録する

## 4. 非機能要件

- 想定処理規模: 数十万〜百万ファイル、TB クラスのデータ量を扱えること
- 処理速度: 大量ファイルのハッシュ計算・走査を、実用的な時間内で完了できること
- 並列処理: 並列 I/O と並列ハッシュ計算を前提とした設計とする
- メモリ効率: 大規模スキャン時でも、一般的な実行環境でメモリ使用量が過度に増大しないこと
- 安全性: 読み取り不能ファイルや破損ファイルについて、全体停止せずに回復可能な形で処理すること

## 5. 技術スタック

- 言語: Rust
- GUI フレームワーク: Tauri
- データベース: SQLite
- 共有コア: 整合性チェック・重複チェックのロジックを Rust crate として共通化する
- GUI / CLI: GUI を基本インターフェースとし、必要に応じて CLI でも主要機能を利用可能とする

### 5.1 採用理由

- Rust は、メモリ安全性と高い処理性能を両立しやすい
- 並列処理と大規模走査に適している
- Tauri により、軽量なデスクトップアプリケーションとして配布しやすい

## 6. データ永続化

- スキャン結果、整合性チェック結果、重複チェック結果、およびメディアごとの履歴は SQLite に保存する
- 1 つのメディアごとに、識別子と最終スキャン時刻を保持する
- メディア識別は、ボリューム ID、デバイスシリアル番号、またはルートボリューム ID を併用して管理する
- 再接続時に識別子が一致した場合、過去のスキャン結果を再利用できるようにする
- 古い履歴は、ユーザー設定または上限管理により削除可能とする

## 7. UI / 出力要件

### 7.1 GUI

- 走査対象、結果サマリー、ファイル単位の詳細を一覧表示する
- 結果をソート、フィルタ、検索可能とする
- アクセス不能ファイル・不一致ファイル・重複ファイルを視覚的に区別する

### 7.2 レポート出力

- CSV / JSON / HTML のうち、少なくとも 1 つの形式をエクスポート可能とする
- ファイル名、サイズ、ハッシュ値、状態、検出時刻を記録する
- レポートはユーザーがそのまま保守・共有できる形式とする

### 7.3 CLI

- 標準出力に結果を出力できる
- 成功・警告・失敗の程度に応じて終了コードを返す
- CI / 自動化利用を前提とした quiet モードや JSON 出力オプションを持つ

## 8. エラーハンドリング方針

- アクセス不可ファイルは警告として記録し、全体の処理を停止しない
- 権限エラー、I/O エラー、ファイル削除競合などは個別にログに残す
- 1 ファイルでエラーが発生しても、他ファイルの処理を継続する
- エラーが多発した場合は、サマリーに件数と影響範囲を出力する
- 重大なシステムエラー時は、ユーザーに説明可能なエラーコードとメッセージを返す

## 9. 用語集

| 用語 | 定義 |
|---|---|
| お手本セット | 正しい状態を定義したファイル一覧。ファイル名・サイズ・ハッシュ値の組み合わせを基準とする。 |
| お手本セット定義ファイル | お手本セットの内容を記述する定義ファイル。JSON または外部ツール互換形式で保持する。 |
| 整合性チェック | お手本セット定義ファイルと対象フォルダの実体を比較し、欠落・破損・改変・不一致を検知する処理。 |
| 重複チェック | 複数フォルダやメディアを横断して、内容が同一のファイルを検出する処理。 |
| リムーバブルメディア識別子 | ドライブまたはメディアの一意な識別情報。再接続時に過去のスキャン結果を紐付けるために利用する。 |

## 10. 未決事項（Open Questions）

以下は次フェーズの設計・実装で詰める項目である。

- ハッシュアルゴリズムの採用（SHA-256 を基本とするか、他の方式を採用するか）
- CLI のサブコマンド構成とオプション設計
- SQLite のテーブル設計、および履歴保持ポリシー
- 外部形式 CSV / XML のフィールドマッピング仕様の詳細化
- GUI の画面一覧と画面遷移
- リムーバブルメディア識別に使う ID の決定（ボリューム ID / シリアル番号 / ルート ID）
- スキャン実行時の進捗表示と中断/再開機能の詳細

## 11. 変更の意図

本修正版では、レビューで指摘された次の3点を要件として明確化した。

1. 比較の基準が曖昧だったため、比較ルールと状態定義を明示した
2. 重複判定のアルゴリズムが未定義だったため、サイズ絞り＋ハッシュ比較を明文化した
3. メディア識別やエラー処理が不足していたため、履歴管理と例外方針を追加した

これにより、設計フェーズでの実装ブレを抑え、機能・性能・運用の整合性を高める。
