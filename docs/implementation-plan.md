# 実装計画（Implementation Plan）

`docs/requirements.md`（10.1〜10.24で確定した仕様）に基づき、実装をボトムアップで進めるためのフェーズ
分割。`docs/open-decisions.md`の7.5・7.6（部分ハッシュ再検討条件／中途比較の将来採用可否）は実装を
ブロックしないため、そのまま先送りとする。

## 進め方の原則

- **ボトムアップ**: 共有コアcrate（ハッシュ→DB→走査→重複/整合性チェック）→CLI→アーカイブ対応→
  パスワード保護→GUIの順。下位層をテストで固めてから上位層を積む。
- **各フェーズは実装だけでなくテストで完了とする**: フェーズ完了の定義は「該当機能のテストが通り、
  `docs/progress-log.md`に結果を記録した状態」とする。
- **進捗の永続化**: 各フェーズ完了時に本ファイルのチェックボックスを更新し、`docs/progress-log.md`に
  実施結果（何を実装したか・テスト結果・気づいた問題）を追記してからコミットする。次フェーズ着手時は
  会話の記憶に頼らず、本ファイルと進捗ログを読み直してから進める。
- **Cargoワークスペース構成**:
  ```
  crates/core/   # 共有コアロジック（§10.13）
  crates/cli/    # CLIバイナリ（§10.16）
  apps/gui/      # Tauriアプリ（§10.14）
  ```

## 依存関係（概要）

```
P0 -> P1 -> P2 -> P3 -> P4
            P3 -> P5
            P4 -> P6
            P5 -> P6
            P6 -> P7
            P7 -> P8
            P7 -> P9
            P8 -> P10
            P9 -> P10
            P10 -> P11
            P6 -> P12 (骨組みのみ先行可)
            P11 -> P12
            P12 -> P13 -> P14
```
P8（リムーバブルメディア）とP9（外部形式取り込み）は互いに独立なので並行可能。

## テスト戦略まとめ

| レイヤ | 手法 |
|---|---|
| ハッシュ・DB・走査 | unitテスト＋一時ディレクトリ/`:memory:`DB統合テスト |
| CLI | スナップショット（`insta`）＋終了コード網羅 |
| アーカイブ生成（TorrentZip/RV7Z） | ゴールデンファイル・決定性（バイト一致）検証 |
| GUI | Tauri command単体＋主要フローE2E＋起動しての目視確認 |
| 性能 | `criterion`ベンチ＋大規模合成データでの負荷試験（P14） |
| クロスプラットフォーム | CI 3OSマトリクス、Windows Tier-1は毎回、macOS/Linux Tier-2は定期的に厚めに検証 |
